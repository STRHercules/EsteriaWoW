# Half-Elf implementation runbook for Codex

## Objective and constraints

Implement playable **Half-Elves on both Alliance and Horde** in the AzerothCore 3.3.5a server and matching client. Both start in **Teldrassil** and know **Common**. The strict finished appearance is a **Human body, proportions, rig, and equipment fit with integrated pointed ears**, for both genders and factions. A Blood Elf donor is an intermediate proof-of-integration only; do not substitute a Blood Elf body for the final requirement. Halflings are out of scope.

Use `HALFELVES.md` as the audit and evidence inventory, not as proof of the active client state. Work in small, verifiable stages. Record the actual IDs, file paths, source rows, commands, and results in a task plan under `.agents/plans/half-elf/` (gitignored). Never guess an unverified race ID or claim gameplay validation from static assets.

Follow `AGENTS.md` and applicable `.agents/docs/` guidance before changing code, SQL, or running tests. The owner has authorized client launch and live database testing, **not** a server configure/build or unrestricted SQL-file edits; request those permissions separately if needed. Do not edit SQL outside `data/sql/updates/pending_db_*/` without explicit permission. Treat existing module SQL as reference until its ownership/update policy is clarified. Do not alter historical SQL. Keep generated client binaries and personal client paths out of commits unless their intended tracked location is agreed. Do not put database credentials in plans, commands captured in logs, commits, or this document; use a secure local connection method and redact output.

## Confirmed environment and remaining decisions

The owner has confirmed:

1. The Human-bodied integrated-ear result is mandatory; **Codex must establish a working M2/SKIN authoring workflow**, since none is currently available.
2. Both factions must be selectable, start in Teldrassil, and learn Common. Test cross-faction starting-zone access, guards, quests, and Common chat; do not assume stock Horde behavior supports this design.
3. The target client is `G:\3.3.5a - Dev\`. Live database testing against the local `acord_world` database on `127.0.0.1` is authorized. Obtain credentials securely from the operator/session rather than embedding them in scripts or this file. Client launch is authorized.

Resolve these policy choices before implementing the affected content: approved classes, racial abilities, whether Horde should have additional language(s), Teldrassil spawn coordinates and hostile-guard/quest treatment, faction-change mapping, and final patch/deployment ownership. Use pending core SQL unless module SQL changes receive explicit authorization. Continue independent work while these decisions are pending.

1. Start with one approved class, **both factions**, and both genders. Use the existing High Elf/Blood Elf pattern as a reference (`modules/mod-worgoblin-high-elf/` and its merge notes); use donor display/model/customization data only for this disposable integration checkpoint. 2. Add the minimum coherent client and server rows needed to make a selectable race: `ChrRaces`, `CharBaseInfo`, `CharStartOutfit`, `CreatureDisplayInfo`, `CreatureDisplayInfoExtra`, `CreatureModelData`, `CharSections`, hair/facial-hair geosets, `NameGen`, `BarberShopStyle`, `SkillRaceClassInfo`, and `SkillLineAbility` as applicable. Copy compatible donor rows with new keys and correct race masks; verify foreign keys/references, textures, and both genders. The server's SQL `ModelName` is not the client's M2 path: the shipped client DBC model chain must resolve to actual packaged files.
3. Add matching server creation/stat/skill/spell/action/start rows for **each faction's ID** and the chosen class (`playercreateinfo*`, `player_race_stats` and relevant masks). Set both start positions to an agreed Teldrassil location and grant Common explicitly; check that Horde characters can spawn and remain there without hostile-guard, phase, quest, or graveyard failures. Read `.agents/docs/sql-guidelines.md` before writing SQL and put core migrations only in pending update directories unless expressly authorized otherwise. Make migrations repeatable according to the project's SQL conventions. Update `SharedDefines.h`, registry, and race-mask-dependent logic as needed; read C++ guidance first.
4. Extend the **actual winning** Glue files (`CharacterCreate.lua/xml`, `CharacterInfo.lua`, `GlueParent.lua`, `CharacterSelect.lua`) for a race slot, faction/ordinal mapping, selection/send ID, labels, icons, portraits, backgrounds, and character-select behavior. 5. Using the authorized client and local test database, create both genders **for each faction**, enumerate, enter the world in Teldrassil, relog, select multiple appearances, equip the starter outfit, and confirm model path/DBC resolution. Test Common chat across faction lines as permitted by the server's chat rules, and identify any required policy/configuration change. Capture the race ID sent by character creation and the saved/reloaded race. If client selection cannot expose a faction choice, diagnose the winning Glue/executable first rather than changing server IDs again.

**Gate:** Demonstrate creation, character selection, login, relog, donor model rendering, and starter equipment for both genders **in each faction**. Label this a prototype, not the finished Half-Elf.

## Phase 3 — author the Human-based Half-Elf model

1. **Establish the missing authoring workflow first.** Inventory available binaries and tool licenses; evaluate WotLK 3.3.5a-compatible M2 import/export and SKIN generation (for example, a Blender-based pipeline plus a version-compatible exporter, or a documented M2/SKIN editor). Verify actual version and round-trip support rather than relying on a tool name or tutorial. Run a no-change Human male/female round trip: import M2 with SKIN LODs, export to new paths, validate binary structures, then load in the authorized client and compare animations, geosets, attachments, textures, and equipment. If no off-the-shelf pipeline works, implement and document a targeted WotLK M2/SKIN transformation pipeline with round-trip tests **before** editing geometry. Keep source project files and reproducible export steps; do not attempt blind byte replacement.
2. Obtain clean WotLK Human male/female M2s, their corresponding SKIN LODs, animations, and texture dependencies from the verified client source. Duplicate them under unique `Character\...` paths, preserving skeleton, animations, geosets, body proportions, attachment IDs, and equipment behavior.
3. Using the proven workflow, integrate pointed ears into each duplicate's head geometry. Rebind all ear vertices to the **Human** head bones; do not copy Blood Elf bone indices into the Human skeleton. Assign Human-compatible UVs/BLPs or author matching ear textures. Preserve face seams, hair coverage, and alpha behavior.
4. Export M2 and **rebuild every required matching SKIN LOD** against its final M2 vertex/index/batch layout. Preserve head attachment 11, hand/weapon/cape attachments, animation links, and geoset visibility. Validate version/structure using `tools/playable_race_pack.py` and available model validators; visually inspect idle, combat, emotes, death, multiple hair choices, and both genders. Copying an unchanged donor SKIN after changing M2 topology is not acceptable.
5. Assign the reserved new model/display IDs to these assets through the winning client DBC chain; update server mirror rows as required. Replace prototype Blood Elf customization with Human-UV-compatible copied rows for **both race IDs**, maintaining unique race keys and consistent face/skin/hair/facial-hair choices. Test every exposed customization combination, including barber changes.
6. Decide the client prefix(es) for both identities and provide gendered head components for them (or a verified compatible reuse strategy). Add/verify `HelmetGeosetVisData`, portrait filenames using each chosen `ClientFileString`, and both races' select/create visuals. Test exposed and covered ears with representative helmets; adjust model/geosets rather than relying on an unsupported separate-ear attachment.

**Gate:** A documented, reproducible authoring workflow produces distinct Human-proportioned player models with integrated pointed ears for both genders across required LODs, animations, customization, and head equipment; both faction identities render them. If existing tools fail, develop/validate the targeted pipeline before claiming the model is done.

## Phase 4 — complete gameplay integration

1. Expand `CharBaseInfo`, `CharStartOutfit`, creation data, stats, skills, spells, actions, and Teldrassil start locations to every approved class on **both faction IDs**; check creation and relog for each. Set faction-specific `ChrRaces.TeamID` and `FactionID`, cinematic (0 if no approved cinematic), and grant Common to both. Verify cross-faction starting-zone guards, quests, graveyards, flight paths, PvP flags, and chat against the actual client/server configuration.
2. Audit race-mask consumers for starter items, armor/weapons, auction, transmog, quests, spells, skill lines, and reputation. Widen only intended masks and verify no `uint32`/high-bit collision; do not blindly copy all Human permissions. Add matching language skill/spell rows so the language is actually learned and usable in chat.
3. Extend stock-race-specific race/faction-change language handling in `CharacterHandler.cpp` and capital taxi initialization in `PlayerTaxi.cpp` if those features are in scope. Map Alliance Half-Elf to Horde Half-Elf and vice versa for approved faction changes; reject unsupported conversions explicitly. Preserve Common per the owner's policy and test whether faction-specific chat restrictions require a deliberate exception. Check team, faction template, starting reputations, and taxi availability after relog and conversion.
4. Test helmets, shoulders, cloaks, shields, ranged/two-handed/sheath positions, transmogs, mounts, flying mounts, vehicles, spell/projectile anchors, and corpse positions. Preserve Human sizing/collision unless observation shows a specific mismatch; Halfling-style runtime scaling is not part of this race.

**Gate:** Each supported class/gender/faction combination can create in Teldrassil, log in, relog, customize, learn/use Common, equip intended items, and perform the approved faction/race-change flows without broken models or permissions.

## Phase 5 — package and hand off

1. Build one coherent client patch from the **winning** DBC baselines plus additive race rows and model/texture/Glue assets. Use the existing race-pack tooling where it supports the task; do not assume it can author M2 geometry. Check archive load order and conflicts with other custom patches; check that server DBCs match client identities and display IDs.
2. Document exact file destinations, patch precedence, SQL migration order, server DBC deployment, registry entries, rollback steps, and prerequisites. Keep generated and source assets clearly distinguished and record source/license provenance where needed.
3. Client launch and local database checks are authorized; follow `.agents/docs/build.md` before running tests, and request explicit permission **before configuring or building** the server. Run appropriate targeted validation and end-to-end tests, and capture evidence for each gate. If a build or live integration step remains blocked, report precisely which gates are unverified rather than declaring completion.

## Completion criteria

- Both faction race IDs are unambiguous in active client, server DBC, SQL, registry, mask logic, and Glue; no existing race row is silently replaced.
- Male and female Half-Elves use distinct Human-rigged, Human-proportioned M2/SKIN assets with visible pointed ears, compatible customization, animation, gear, and helmets.
- Every approved class on both factions creates in Teldrassil, enumerates, enters the world, relogs, and retains appearance, team, Common, skills, items, and intended permissions.
- The distributed client patch wins archive precedence and resolves every referenced DBC/model/texture/UI path; server deployment and rollback are documented.
