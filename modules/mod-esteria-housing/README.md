# mod-esteria-housing

Player housing, Phase 1 slice. The design lives in the wowdecomp repo under `docs/housing/`; the client side is
wowdecomp `Extensions/Housing` and `Addons/EsteriaHousing`.

- One house per account, claimed from the Housing Steward (creature 9500100, `npc_esteria_housing_steward`).
- Each house is its own instance of map 35 (Stormwind Vault, unused). The steward inside is the exit.
- Group members can visit each other's houses through the steward. Only the owning account can edit.
- Decor is temporary GameObjects (templates 9500000+, display rows 60000+, `retail\<FDID>.m2` on the client).
- Edits arrive as `CMSG_ESTERIA_HOUSING_EDIT` and are validated by `src/HousingRules.h` in protocol order.
  - Each accepted edit is persisted in one characters-DB transaction.
  - Then the GO is respawned and the new state goes to everyone inside.

## Flags

`conf/esteria_housing.conf.dist`. `EsteriaHousing.Enable = 0` by default. While it's off, the instance hook is null
and the steward says housing isn't available. HELLO is still answered, with `enabled = 0`.

## Data (not auto-applied)

The SQL lives in `sql/`, not `data/sql/`, so the AzerothCore updater never applies it to a live realm.

- `sql/world/housing_world.sql` is generated by `tools/make_slice.py`. Its rollback is `housing_world_rollback.sql`.
- `sql/characters/housing_characters.sql`. Its rollback is `housing_characters_rollback.sql`.
- `sql/world/housing_commerce_world.sql`: merchant template pool and service objects for shops and commissions (hand-written, not generated).
- `sql/world/housing_adventure_world.sql`: training dummies, portals, meeting stones and the home spells (generated by `tools/make_adventure.py`).
- `sql/world/housing_collections_world.sql`: trophies, mount displays, mannequins, the library and pet habitats (hand-written).
- `sql/world/housing_household_world.sql`: household services, storage chests, crafting stations and the House Hearthstone
  (generated by `tools/make_household.py`). Apply the world files in this order, after `housing_world.sql`, which rebuilds the catalog.

`tools/make_slice.py` also writes the client patch `Patch-ZZZZZZZZZZZZZZZZZZZZZZZZZHousingDev.MPQ`. That is the
winning `GameObjectDisplayInfo.dbc` plus the 20 decor rows.

## Tools

- `tools/build.py [image:tag]` builds worldserver in the `housing-build` container. That container is a snapshot of
  `coa-lead`, so the shared tree is untouched. The script can also package an image.
- `tools/stage.py dump|clone|apply|rollback|test-migration|start <image>|check|stop` manages the stage realm.
  - It uses the `housing_dev_*` clones, a worldserver on 8099 and an authserver on 3725.
  - It never writes `acore_*`.
- `tests/rules_test.cpp` tests validation and runs without a server:

  ```sh
  g++ -std=c++20 -I src tests/rules_test.cpp -o rules_test && ./rules_test
  ```

## Known limits (slice)

- The room bounds are a provisional box around the map 35 entry point. They are not measured.
- Houses and placements are all loaded at startup.
- The return point after leaving is kept in memory only. After a restart, leaving sends you to your hearthstone.
- Visiting goes through stock instance entry. AzerothCore's 5-instances-per-hour limit still applies to visitors who
  hop between houses.
- There is no server collision or LOS for decor. vmaps can't read MD21 models, and movement is client-authoritative.
